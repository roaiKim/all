# 司机端运输执行 · 小程序接口对接文档

日期：2026-11-16。适用后端：`comma-inovance-tms` 本轮新增司机作业适配接口。依据：运输执行 PRD、`司机端-运输执行.html` 及当前实现。

**交付状态：供小程序开发对接的接口契约，后端仍在做最终编译、回归和联调收尾，尚未部署，不能据本文推断测试环境已经开通。本文不包含小程序页面实现。** 登录复用项目现有账号密码流程；短信为 PRD 扩展能力，不要求现有登录切换到短信。

## 1. 公共约定

### 1.1 地址、认证和响应

业务网关前缀：`/tms/driverExecution`。以下接口清单省略此前缀；登录使用 `/auth`，不使用运输业务前缀。实际域名由部署环境提供。

```http
Authorization: Bearer <ACCESS_TOKEN>
Comma-Tenant-Id: <CURRENT_TENANT_ID>
Content-Type: application/json
```

文件上传改用 `multipart/form-data`，由上传组件生成 boundary。文件预览、下载同样携带访问令牌和租户头。不得在 URL 中传令牌。

业务响应沿用现有 `R<T>`，结构示意：

```json
{
  "code": 200,
  "success": true,
  "data": {},
  "msg": "操作成功"
}
```

鉴权失败可能返回 HTTP 401/403，业务校验失败走项目现有异常响应。小程序同时判断 HTTP 状态、`success/code`，显示后端 `msg`；不能只判断 HTTP 200。OAuth 令牌响应和文件二进制流不套 `R`。

所有业务 ID 按**字符串**保存和提交：`entrustId`=运输委托 LD、`taskId`=真实运输任务 TT、`orderId`=运输订单 TO、`podId`=某批次签收单、`attachmentId`=公共附件 ID。禁止先转换为 JavaScript Number。数量、重量、体积仍为数值，`null` 表示未知，不能显示成 0。

时间统一理解为业务服务器本地时间，部署应使用 `Asia/Shanghai`。签收请求推荐 `2026-11-16T10:30:00`，不带时区后缀；展示兼容服务端现有时间序列化格式。提货 `pickupTime` 额外兼容既有毫秒时间戳和 `yyyy-MM-dd HH:mm:ss` 格式，建议省略，由服务器记当前时间。

### 1.2 任务授权与版本

身份来自可信令牌中的司机账号及当前租户司机档案映射，按 `execution_vehicle` 实际派车授权；没有车辆子表时才兼容旧主司机字段。客户端不传司机身份决定权限。同一 LD 下只返回当前司机可见 TT/TO，不获得其他司机作业权限，也不返回费用实体。

写操作必须携带 `requestId` 和 `expectedVersion`：

| 字段 | 规则 |
| --- | --- |
| `requestId` | 8～64 位字母、数字、下划线或连字符；一次正式动作一个值，例如 UUID |
| `expectedVersion` | 对应 TT 最近读取的版本原样提交；不同 TT 不能混用 |
| 读取版本 | 提货详情 `tasks[].expectedVersion`；签收详情 `tasks[].version`；待签货物、历史记录详情 `version`；异常准备 `expectedVersion` |
| 成功后 | 更新版本并刷新详情、列表统计；不能继续使用提交前版本 |
| 网络超时 | 原请求号、原内容重试；成功结果可重放，不重复写正式业务 |
| 版本过期 | 重新读取并让用户核对；新一轮确认使用新请求号，不在原请求号上改版本或内容 |

同请求号不同内容拒绝；业务失败与幂等记录一起回滚。即使重放成功结果也重查当前授权，改派后不能靠旧请求号读他人任务。正式提货、签收、上报必须在线提交；页面取消、离线缓存、上传成功均不代表业务完成。

取消、挂起、改派、路线/货物/包装/回单变化均可能使原页面不可提交，以服务器最新校验为准。司机旧 PC 通用实体 CRUD 路径不能替代这些受控接口。

## 3. 任务查询和个人页面

### 3.1 Q01 首页/我的任务

```http
POST /tms/driverExecution/tasks/page
```

```json
{"pageNo":1,"pageSize":20,"tab":"PICKUP","viewMode":"ENTRUST","status":"ALL","keyword":""}
```

| 字段 | 说明 |
| --- | --- |
| `pageNo/pageSize` | 默认 1/20，每页 1～100 |
| `tab` | `PICKUP` 提货、`RECEIPT` 签收 |
| `viewMode` | 提货只支持 `ENTRUST`；签收默认 `ORDER`，可选 `ENTRUST` |
| `status` | 提货：`ALL/WAIT_CHECK_IN/WAIT_PICKUP/PICKED_UP`；签收：`ALL/WAIT_RECEIPT/PARTIAL_RECEIPT/RECEIVED` |
| `keyword` | 可选，最长100；委托、任务、订单、物流单号、车牌及客户等当前展示字段搜索 |

`data` 包含 `records,total,pageNo,pageSize,tab,viewMode,statistics,scope`。`scope=CURRENT_ASSIGNMENT`。`statistics` 按当前 Tab、维度和关键词计算，包含 `ALL` 与各状态数，不因当前选中的状态缩小统计。待办优先，其次计划时间，最后稳定 ID 排序。

`ENTRUST` 卡片包含 `entrustId,entrustNo,entrustStatus,displayStage,planTime,tasks[]`；一张卡片下可能有多个本人 TT，提交时必须选择具体 `taskId`，不能拿 LD 代替 TT。本人卡片完成只表示可见任务完成，不等于整个 LD 全局完成。

`tasks[]` 包含 `taskId,taskNo,taskStatus,logisticsNo,truckNo,driverName,driverPhone,planTime,plannedArrivalTime`。提货数量为 `totalPackageCount/completedPackageCount/pendingPackageCount`，签收数量为 `totalPackageCount/signedPackageCount/pendingPackageCount`。`ORDER` 卡片另有 `orderId,orderNo,orderStatus,unloadPointId,customerName,consignee,signStatus,canSign,blockedReason`。

实装指标字段：`actualMaxPackageCount` 最大包装件数、`actualPalletCount` 托数、`actualLooseBoxCount` 散箱数、`actualBoxCount` 箱数、`actualGrossWeight` 毛重、`actualNetWeight` 净重、`actualVolume` 立方米体积。件数与 PCS 不互相替代，同箱多个 SKU 不重复计箱，未知字段保持 `null`。

### 3.2 Q02 提货详情

`GET /entrusts/{entrustId}/pickup?taskId=<可选真实TT>`

返回 `entrustId,entrustNo,entrustStatus,tasks[]`。不传 taskId 时返回该 LD 下所有本人可见 TT；每个 TT 都有独立 `expectedVersion`。

| TT 字段 | 含义 |
| --- | --- |
| `displayStage` | `WAIT_CHECK_IN/WAIT_PICKUP/PICKED_UP` |
| `routeValid/blockedReason` | 路顺是否合法、不能操作的原因 |
| `totalPoints/completedPoints` | 当前 TT 真实提货点进度 |
| `nextPickupPointId/allPickupCompleted` | 下一个允许确认的点、当前 TT 是否全提 |
| `materialApplicable/materialRequired` | 场景是否适用/是否必填集装箱资料 |
| `voucherRequired` | 是否按场景在末点强制检查提货凭证 |
| `canSaveContainerMaterial` | 是否允许独立补料 |
| `containerMaterial` | 已保存箱号、封号、皮重、货重、VGM |
| `deliveryCopies` | 已保存送货单份数 |
| `pickupPoints[]` | 当前 TT 各真实提货点 |

每点字段：`pickupPointId,pointIdentitySource,sequence,name,address,contact,phone,planTime,orderIds,checkedIn,checkedInAt,pickupConfirmed,actualPickupTime,state,canCheckIn,canConfirmPickup,deliveryCopies` 及实装指标。

点 ID 由后端生成并原样回传：真实路顺为 `ROAD_<路顺节点ID>`；仅有一个地址组且无真实路顺时才允许 `SINGLE_<稳定地址标识>`，其来源为 `ADDRESS_SINGLE`。多点缺真实路顺、地址缺失或路顺不一致会拦截，客户端不得用数组下标或自行拼地址生成点 ID。

按钮使用 `canCheckIn/canConfirmPickup/canSaveContainerMaterial` 控制；服务器提交时会再次校验。已提点不要求补造签到事实。

### 3.3 Q03 提货/送货货物明细

```json
{"entrustId":"101","taskId":"201","orderId":null,"pickupPointId":"ROAD_901"}
```

`POST /cargo/query` 至少指定 LD、TT 或 TO 中一个范围。可按 `orderId` 收窄；`pickupPointId` 与 `unloadPointId` 分别用于提货点、卸货点，二者不能同时传。若父级与订单、点不一致或点已变化会拒绝。

返回 `tasks[]`，每项包含 `entrustId,taskId,taskNo,version,orders[]` 及实装指标；每 TO 返回 `orderId,orderNo,unloadPointId,customerName,pickupAddress,deliveryAddress,cargoSource,packageLines[],planLines[]`。

`packageLines` 为真实装箱明细：`packageId,materialCode,materialName,customerPo,pcs,unit,boxNo,packingNo,palletNo,maxPackageType,boxLengthMm,boxWidthMm,boxHeightMm,boxWeightKg,boxVolumeCbm`。它是 SKU 行列表，不能直接把行数当箱数，整单箱托汇总以返回指标为准。

无实装时 `cargoSource=PLAN`，`planLines` 仅展示实际计划物料、数量及原始单位，不按 PCS 虚构箱数。司机不开放改量接口；发现数量不符联系仓管/调度，修改后重新读取版本。

### 3.4 Q09 我的、Q10 运输记录、Q11 轨迹

- `GET /me`：返回 `driverId,name,phone,vehicles[],settingsAvailable:false`。我的任务复用 Q01。原型“设置”无已定义内容，不新增设置保存接口。
- `POST /transport-records/page`：请求 `pageNo,pageSize,taskId?,fromTime?,toTime?`；返回 `records,total,pageNo,pageSize,historyScope,historyHint`。每条为 `recordId,entrustId,taskId,operation,operatedAt,taskNo,entrustNo,truckNo`。
- 当前运输记录范围为 `OWN_DRIVER_OPERATION_SNAPSHOTS`：本人使用新司机入口留下的操作快照，可在改派后只读本人历史；**不等于全部旧运输任务归档，也不因此开放改派后的当前货物、POD和文件**。存量记录缺少快照字段时返回空，不用他人当前信息补齐。
- `GET /tasks/{taskId}/tracking`：返回 `taskId,nodes[],trackingKind:REPORTED_NODES,empty,hint`。节点字段 `code,name,time,content,address,longitude,latitude,source`，无数据返回空；这是实际上报轨迹节点，**不是持续实时 GPS**。查看静态路顺用详情中的点，不将静态地址造为轨迹位置。

## 4. 签到、提货确认和集装箱补料

### 4.1 W01 点签到

```json
{
  "entrustId":"101",
  "taskId":"201",
  "pickupPointId":"ROAD_901",
  "requestId":"pickup_checkin_20261116_001",
  "expectedVersion":"<Q02该TT版本>"
}
```

`POST /pickup-points/check-in` 对应“司机签到”二次确认后的最终动作。时间由服务端记录；取消确认不调用。签到事实独立保存，并投影当前点待提 TO 为待装车。重复或后阶段不会回退已提货。

成功返回**单 TT 提货详情**，含新 `expectedVersion`；与聚合 Q02 的 `tasks[]` 包装不同。成功后刷新列表/详情。

### 4.2 W02 点确认提货

```json
{
  "entrustId":"101",
  "taskId":"201",
  "pickupPointId":"ROAD_901",
  "requestId":"pickup_confirm_20261116_001",
  "expectedVersion":"<签到后最新版本>",
  "deliveryCopies":2,
  "containerMaterial":{
    "containerNo":"<实际柜号>",
    "sealNo":"<实际封号>",
    "tareWeight":2300,
    "cargoWeight":12600,
    "vgmWeight":14900,
    "vgmCorrectionReason":null
  },
  "attachmentIds":["401"]
}
```

`POST /pickup-points/confirm`：先完成当前点签到，并按真实路顺依次确认。首点资料弹窗只有最终二次确认后提交；用户取消时不先调用补料接口。后续点复用同一命令，仅当前点处理，不提交整 LD 其他 TT。

- `deliveryCopies` 可省略沿用当前值；传入必须正整数，0、负数、小数拒绝。
- `containerMaterial` 按 `materialApplicable/materialRequired` 展示和必填；不适用场景不要无故强制填柜信息。
- 重量不能为负，VGM 与皮重加货重不一致需修正原因，沿已有后端业务校验。
- 当前明确要求资料的场景包括中港段整车、境内整柜交仓段整车及跨境整柜，以实际返回场景规则为准。
- 提货凭证按场景在末点必传，中港/整柜交仓不能绕过；单提货点同时是首末点。
- `pickupTime` 可省略默认当前。现有主链限制显式时间不能早于当前1分钟，新入口同时拒绝未来时间；不支持司机历史提货补录。
- 末点凭证由真实任务附件关联核验。F01 上传成功并不等于提货成功；只传文件名、照片张数或 URL 无效。

成功返回单 TT 最新提货详情，另有 `confirmedPickupPointId`，使用 `nextPickupPointId/allPickupCompleted` 继续。当前点提货、资料、送货单份数、状态/节点及既有仓储联动在正式命令内处理。

PC 可以依既有业务代确认提货而不要求司机签到；司机入口要求签到。PC 撤回保留真实签到事实，有签到则回到待提货/待装车投影，无签到旧业务按原规则回退；小程序重新读取状态和版本，不本地推演。

### 4.3 W03 独立补料

`POST /container-material/save` 共用 W02 请求结构中的 `entrustId,taskId,requestId,expectedVersion,containerMaterial`，无需 pickupPointId。只在 `canSaveContainerMaterial=true` 时展示入口，按现有 FR-11 状态及场景校验。成功返回单 TT 最新提货详情。

原型主要通过首点弹窗采集资料，没有完整独立补料入口；若小程序接入独立补料，调用此接口。只读展示不是保存。

## 5. 签收、分批记录与回单

### 5.1 Q04/Q05 打开页面与修改本次明细

`GET /entrusts/{entrustId}/receipts?taskId=<可选>&orderId=<可选>`

返回 `entrustId,tasks[],signStatusOptions,abnormalReasonOptions,receiptKindPolicy,receiptKindHint,interceptPolicy,interceptHint,attachmentPolicy`。

每 TT：`taskId,taskNo,logisticsNo,truckNo,driverName,driverPhone,plannedArrivalTime,version,unloadPoints[]`。每卸点：`unloadPointId,name,address,contact,phone,orders[]`。每 TO：`orderId,orderNo,unloadPointId,customerName,consignee,status,signStatus,totalPackageCount,signedPackageCount,pendingPackageCount,signingBasis,packageGroups,canSign,blockedReason,transportRequirements`。

点“修改签收明细”调用 `GET /orders/{orderId}/receivable-cargo`，返回该 TO 以上字段，并补充 `entrustId,taskId,version`。只有后端返回的真实剩余 `packageGroupId` 可用于提交。

`packageGroups[]` 每组是一件可完整处理的物理包装，字段包括 `packageGroupId,packageCount:1,boxNo,maxPackageSequence,boxLength,boxWidth,boxHeight,weight,volume,items[]`；SKU 为 `itemCode,itemName,pcs,customerProductCode`。返回的 `measurementBasis=BOX/PALLET/UNKNOWN`、`dimensionUnit=MM`、`weightUnit=KG`、`volumeUnit=M3` 及 `measurementHint`用于区分箱和国际外包装；不可把托尺寸当单箱尺寸。未知测量保持空。

**小程序不能再按原型随机拆分 SKU 60%/40% 或仅上传一个本次箱数。** 如果界面采用“每 SKU 输入件数”，必须解析为返回的完整包装组集合，同箱所有 SKU 一起处理，不能拆半箱或重复占箱。无法唯一匹配时应让用户选择实际包装。

无实装/`PLAN_CARGO`、地址缺失或包装身份不完整会返回 `canSign=false/blockedReason`；司机端不按 PCS 模拟箱数。此时联系调度核实，不能伪造 packageGroupId。

### 5.2 W05 预校验与 W06 正式确认

两个接口请求结构相同：

```json
{
  "entrustId":"101",
  "taskId":"201",
  "unloadPointId":"<Q04返回的真实卸点ID>",
  "requestId":"receipt_confirm_20261116_001",
  "expectedVersion":"<当前TT的version>",
  "signTime":"2026-11-16T10:30:00",
  "signer":"张先生",
  "orders":[
    {
      "orderId":"301",
      "signStatus":10,
      "remark":null,
      "reasonCode":null,
      "packageGroupIds":["<真实包装组ID-1>","<真实包装组ID-2>"],
      "attachmentIds":["<该TO上传RECEIPT所得ID>"]
    }
  ]
}
```

| 字段 | 约束 |
| --- | --- |
| `unloadPointId` | 必须为当前 TT 真实卸点；一批不能跨 TT/卸点 |
| `orders` | 1～100 个 TO，不得重复；允许只选一个 TO |
| `packageGroupIds` | 每 TO 1～2000 个真实完整待签组，不得越权、重复或超待签 |
| `signTime` | 可省略默认当前；传入按服务器签收时间规则校验，不允许未来时间 |
| `signer` | 可选，最长100 |
| `remark` | 最长1000，异常签收必须明确填写非空原因 |
| `reasonCode` | 可选 `DAMAGE/SHORTAGE/DEFORMED/OTHER`，校验后与原因一起持久化，总长度仍受限 |
| `attachmentIds` | 可选，每 TO 最多20个；须为本人同任务、同 TO、RECEIPT 的有效草稿 |

四种结果必须逐 TO 保存：

| `signStatus` | 展示 | 包装处理与实收 |
| --- | --- | --- |
| 10 | 正常签收 | 消费选中包装，计实收 |
| 20 | 异常签收 | 原因必填，消费选中包装并计实收 |
| 30 | 已拒收 | 生成正式拒收记录，实收0；所选包装保留可再次签收 |
| 40 | 已拦截 | **沿现有 PC 口径：消费选中包装并计实收** |

**拦截计实收是保留的现行业务语义，不按名称自行改成零实收；该口径仍需产品确认。** 返回 `interceptPolicy=CONSUME_SELECTED_PACKAGES` 和提示。异常签收并不自动等同于正式运输异常单，正式异常需另走 W04。

`POST /receipts/validate` 对应明细保存前检查/确认弹窗摘要，不生成 POD。返回 `valid:true,createsReceipt:false,version,orders,processedPackageCount,actualPackageCount,receiptKindPolicy`。弹窗展示“本次”处理量/实收量，不展示全部待签数冒充本次数量；取消弹窗不调用 W06。

`POST /receipts/confirm` 对应最终“确认签收”。同批全部 TO 同事务，任一个非法则整批失败。成功返回：

```json
{
  "requestId":"receipt_confirm_20261116_001",
  "receipts":[{
    "podId":"501","podNo":"<生成的POD号>","orderId":"301","signStatus":10,
    "processedPackageCount":2,"actualPackageCount":2,
    "receiptKind":null,"requiresClassification":true
  }],
  "processedPackageCount":2,
  "actualPackageCount":2,
  "signTime":"<服务端签收时间>",
  "version":"<新版本>",
  "entrustStatus":80,
  "taskStatus":80
}
```

示例状态值仅说明字段，不应硬编码成功后一定变成80。先签95箱再签5箱是两次合法批次、两份历史结果；第二批重新加载剩余包装和版本。成功后再次提交同请求号重放原结果，不能重复签成第三批。

### 5.3 回单分类与凭证

新司机 POD `receiptKind=null`、`requiresClassification=true`，等待 PC 按真实业务选择 ORDER/TRANSPORT 分类。司机不提交分类字段，不能通过客户端分类绕过回单工作流。创建 POD 可同时携带凭证，但**有凭证不表示自动分类、审核或归档**。

签收照片选传，建议在 W06 前按每 TO 上传 `purpose=RECEIPT` 草稿并随该 TO 提交。同一草稿只能消费给一个 TO/POD；同一图片若确实适用于多个 TO，需为各 TO 分别创建独立上传引用，不能在多 TO 里重复同一个草稿 ID。

### 5.4 Q06/Q07 分批签收记录

`POST /receipt-records/page`：

```json
{"entrustId":"101","taskId":"201","orderId":"301","pageNo":1,"pageSize":20}
```

LD/TT/TO 至少传一个，若同时传则必须一致；最多每页100。返回 `records,total,pageNo,pageSize`，按签收时间倒序、ID倒序。

记录字段：`podId,podNo,orderId,orderNo,signTime,recordedAt,signer,signStatus,signStatusName,remark,processedPackageCount,actualPackageCount,signingBasis,receiptKind,receiptWorkflowStatus,attachments[]`。

`GET /receipt-records/{podId}` 另返回 `entrustId,taskId,version,details[]`；每明细包含 `detailId,boxNo,maxPackageNo,itemCode,expectedPcs,actualPcs,signingBasis`。拒收明细实收0，不将曾经拒收覆盖为后来正常签收。

附件为公共 `Attachment.id`，按 F03/F04 鉴权读取；历史附件可通过相同接口访问，不直接拼对象存储路径。历史 POD 仍要求当前任务有效授权，改派或 TO 取消后不凭“曾经参与”开放后续 POD/文件。

## 6. 文件上传、列表、预览、下载、删除

### 6.1 F01 上传

`POST /files/upload`，multipart 表单：

| 参数 | 必填 | 含义 |
| --- | --- | --- |
| `entrustId` | 是 | 当前 LD |
| `taskId` | 是 | 当前本人 TT |
| `orderId` | RECEIPT必填 | 真实 TO，其他用途可选；不能跨任务 |
| `purpose` | 是 | `PICKUP/RECEIPT/EXCEPTION` |
| `file` | 是 | 真实二进制文件，一次一份 |

| 用途 | 格式 | 单文件上限 | 生命周期 |
| --- | --- | --- | --- |
| PICKUP 提货凭证 | JPG/JPEG/PNG | 5MiB | 上传即绑定 TT，提货完成/有效放行后只读 |
| RECEIPT 签收回单 | JPG/JPEG/PNG/PDF | 10MiB | 先为24小时草稿，正式签收/补传后消费绑定 POD |
| EXCEPTION 异常证据 | JPG/JPEG/PNG | 10MiB | 先为24小时草稿，正式上报后消费 |

当前用途/订单草稿或可编辑文件数量最多20；正式每次最多20份。同任务的他人文件可在业务证据范围内查看，但不能拿他人草稿进行消费或删除。

图片校验真实内容，边长不超过12000、总像素不超过2500万。现有回单 PDF 校验要求**每份 PDF 恰有一张图片**；加密、纯文本、含多张图片等不符合现有规则的 PDF 会拒绝。多页凭证可上传多份 JPG/PNG，不应把接口描述为任意 PDF 均可用。

响应 `data` 为 `attachmentId,fileName,fileSize,purpose,state,orderId,expiresAt,canDelete,canPreview,canDownload` 等文件摘要，不包含公开对象路径。`attachmentId` 才是后续操作标识。

### 6.2 F02 文件列表

`POST /files/query` 请求 `entrustId,taskId,orderId?,podId?,purpose`。查询当前草稿/提货文件需有效 TT 上下文，查询指定 POD 可传 `podId`；其他父级范围若同时传，必须一致。

- `purpose=PICKUP`：返回当前任务真实提货凭证，包括兼容存量业务文件。
- `purpose=RECEIPT/EXCEPTION` 且无 POD：仅回显本人未消费有效草稿，可按 orderId 收窄。
- `podId`：返回该 POD 的正式回单附件，按当前任务/TO授权。

### 6.3 F03/F04 预览、下载

返回 `Content-Type` 对应的真实文件流、UTF-8文件名、`Cache-Control:no-store`、`X-Content-Type-Options:nosniff`。预览为 inline，下载为 attachment。未知历史格式仅允许二进制下载，不伪装成图片预览。

小程序用带认证头的下载能力取得临时本地文件后预览，不能把需要 Bearer 的 URL 直接当永久公共图片地址。预览失败保留明确提示，不转用可绕过鉴权的旧 URL。

### 6.4 F05 删除及清理

只允许删除本人未消费草稿或仍可编辑的本人提货凭证。已消费签收/异常文件、归档回单、提货全完成或已有有效放行的证据拒绝删除。后端逐次重查权限和锁定状态，按钮隐藏不能替代服务端校验。

草稿过期不再允许消费。远端文件元数据与本地数据库不属于同一个事务，后端使用持久清理任务重试解绑/独占孤立对象清理，保留共享 POD 对象。后台全量过期清理需在部署中启用 `driver.execution.file-cleanup.enabled=true`；默认关闭，不应以“草稿过期不可用”误认为物理文件已即时删除。

## 7. 登录与异常上报

### 7.1 登录：优先复用现有账号密码

#### 7.1.1 账号密码请求

本轮没有要求前端切换登录方式。已有司机账号可复用项目现有 OAuth 密码登录；需使用实际环境登记的客户端认证与 scope，并联调验证该账号、客户端和网关配置。

```http
POST /auth/oauth2/token?grant_type=password
Auth-Sub: MINI_APP
Authorization: Basic <REGISTERED_CLIENT_AUTHORIZATION>
Content-Type: application/x-www-form-urlencoded

username=<EXISTING_ACCOUNT_OR_PHONE>&password=<URL_ENCODED_RSA_BASE64_PASSWORD>
```

- `username` 是已有账号或手机号，不自动注册账号。
- `password` 复用现有前端 `src/utils/index.ts` 的 `encrypted()` 约定：JSEncrypt 使用与环境私钥匹配的 RSA 公钥加密，结果为 Base64，再进行表单 URL 编码。不能直传明文，也不能把 `+` 当空格。
- `grant_type=password` 放在 query，供现有网关读取。表单中不重复提交同名参数，避免授权转换器判定重复参数。
- 当前 `MINI_APP` 主体调用已有账号查询并正常校验密码，同时跳过 PC 图形验证码。若使用 PC 主体 `user`，还要提供现有图形验证码 `code` 和 `randomStr`；此 `code` 不是短信验证码。
- `Auth-Sub: driver` 的现有账号密码分支明确返回“不支持司机平台登录”，不能用于上述密码请求。
- 客户端目前支持现有 `client_secret_basic` / `client_secret_post`，具体认证值由环境提供，不把生产密钥写入本文或新发放到小程序包。本轮未新增 BFF URL，也不以新增 BFF 作为复用现有流程的前置条件。

账号必须真实为司机类型 `userType=2`，并通过可信 `Tenant-Driver-Ids` 关联目标租户司机档案。仅切换登录主体不会把平台账号变为司机。登录成功后，改派、取消、挂起或任务不在可操作阶段仍可能禁止作业。

成功返回 OAuth 原生 JSON，不套业务 `R`：

```json
{
  "access_token": "<ACCESS_TOKEN>",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "<REFRESH_TOKEN>",
  "scope": "<REGISTERED_SCOPE>"
}
```

`expires_in` 以实际响应为准；未登记刷新授权时没有刷新令牌。登录错误也使用 OAuth 原生错误，不能只按业务 `R.code` 判断。

#### 7.1.2 刷新、退出与联调边界

认证服务支持 `refresh_token` 授权，使用原客户端和 `refresh_token`；退出复用 `DELETE /auth/token/logout`。**目前源码中的网关 `PasswordDecoderFilter` 对普通令牌请求仍要求 `username/password`，只提交刷新令牌会被拦截；原前端刷新调用也处于注释状态。** 因此不能把“仅提交 refresh_token 即可经过现有网关”写成已验证能力。接入方先按现有登录流程处理到期重登，刷新直通需要网关联调或单独补齐。

后端保留司机严格 7 天会话扩展：可信司机首次签发令牌写入绝对 `driver_session_expires_at`，后续刷新沿用原始截止时间，网关同时检查截止。旧令牌按原刷新令牌签发时间兼容计算。`driver.execution.oauth-client-id` 指定司机客户端后，该客户端刷新令牌固定 7 天并复用，不滚动续期。平台账号沿用原配置。这是保留的 PRD 扩展，不要求用户改变账号密码登录方式。

#### 7.1.3 可选 PRD 扩展：短信验证码

短信扩展保留，非当前小程序账号密码对接的强制要求。

| 操作 | 接口 | 约定 |
| --- | --- | --- |
| 获取司机短信验证码 | `POST /admin/mobile/driver/{mobile}` | 已登记、启用且未锁定的司机账号；真实短信模板发送，响应不返回验证码 |
| 短信授权 | `POST /auth/oauth2/token?grant_type=sms_code` | `Auth-Sub: driver`，form `mobile`、`code`，使用已有登记客户端 |

验证码有效 300 秒，同手机号发送限流 60 秒，已有有效码不重新发送；错误累计 5 次原子锁定 1800 秒，正确验证码只消费一次。获取验证码成功使用业务 `R<Boolean>`，`data=true`，`msg=验证码已发送，5分钟内有效`。

短信模板配置：`driver.execution.sms.template-id` 必须为有效模板 ID，`driver.execution.sms.code-parameter` 默认为 `code`。未配置模板或真实发送失败会报错，不模拟成功。客户端需登记 `sms_code` 授权（历史 `mobile` 会映射）。**同样受当前 `PasswordDecoderFilter` 限制，只有 `mobile/code` 的短信请求尚需补齐网关直通或按实际环境验证；不要在小程序中把它当作已经联通的登录入口。**

### 7.2 异常上报准备

`POST /tms/driverExecution/exceptions/prepare`

对应页面：从提货或签收卡片点击“异常上报”，打开弹窗时调用；切换受影响订单范围后可以重新调用。只读取上下文，不生成异常单。

```json
{
  "entrustId": "101",
  "taskId": "201",
  "orderIds": ["301", "302"],
  "stage": "PICKUP"
}
```

| 请求字段 | 必填 | 说明 |
| --- | --- | --- |
| `entrustId` | 是 | 当前授权 LD |
| `taskId` | 是 | 当前司机实际执行的 TT；不能只传 LD 后让后端任取任务 |
| `orderIds` | 否 | 本次受影响 TO，最多 100 个且不能重复；不传、`null` 或空数组均明确表示当前 TT 的全部有效 TO，不能理解为“不关联订单” |
| `stage` | 否 | 入口阶段 `PICKUP` 或 `SIGNOFF`；小程序应按实际入口填写 |

成功 `R.data` 中的字段：

| 字段 | 含义 |
| --- | --- |
| `entrustId`、`taskId` | 已授权的真实上下文 |
| `expectedVersion` | 当前任务版本，正式上报时原样提交；不可自行计算 |
| `stage` | 本次传入入口阶段 |
| `orderScope` | 当前默认范围说明，现为“未指定orderIds时关联当前TT全部有效TO” |
| `orders[]` | 选中范围内真实订单 |
| `orders[].orderId`、`orderNumber` | TO ID、TO 单号 |
| `orders[].materialCodes[]` | 此 TO 可关联的真实物料编码；不要从其他订单复制编码 |
| `categories[]` | 固定七种展示类别及当前实际可提交状态 |
| `categories[].code`、`name` | 司机端展示代码和名称 |
| `categories[].enabled` | 是否至少有一个无后台编码歧义的有效级别 |
| `categories[].disabledReason` | 禁用原因；可用时为 `null` |
| `categories[].levels[]` | 当前类别实际允许的级别，字段为 `code`（整数）与 `name` |
| `levelRequired` | 当前为 `true` |
| `descriptionRequired` | 当前为 `true` |
| `evidenceRequired` | 当前为 `false`，对应当前手工异常提交链；不能推断未来专项规则永远不要求证据 |
| `maxDescriptionLength` | 当前为 2000 |

类别示例，仅说明结构，不能据此写死实际可选级别：

```json
{
  "code": "DAMAGE",
  "name": "货物破损",
  "enabled": true,
  "disabledReason": null,
  "levels": [{"code": 3, "name": "一般事件"}]
}
```

#### 7.2.1 七类稳定展示代码

| `categoryCode` | 展示名称 |
| --- | --- |
| `DAMAGE` | 货物破损 |
| `LOSS` | 货物丢失 |
| `QUANTITY` | 数量不符 |
| `ADDRESS` | 地址错误 |
| `REFUSED` | 客户拒收 |
| `TRAFFIC` | 交通异常 |
| `OTHER` | 其他 |

七类代码只是司机端契约，不等于后台 `exceptionTypeCode`/`exceptionCode`。后端只读取当前租户启用且未删除、字段完整的真实异常规则：优先使用配置的 `类型编码:异常编码` 精确映射；未配置时仅接受规则异常名称与上述展示中文精确一致的匹配。同一级别存在多个后台编码时，不向小程序提供这一歧义级别。

小程序渲染 `enabled=false` 的项应提示 `disabledReason` 并禁止提交。不得将“货物丢失”自行改成后台“货物灭失”，不得将“交通异常”自行改成“运输延误”，不得把未选级别写成“一般”。原型缺少级别控件，小程序对接时须增加实际有效级别选择；当前接口不替客户端默认级别。

### 7.3 异常证据照片

异常弹窗拍照和相册选择共用：

`POST /tms/driverExecution/files/upload`

`multipart/form-data` 参数：`entrustId`、`taskId`、`purpose=EXCEPTION`、二进制 `file`；可选 `orderId` 用于当前任务内订单作用域。返回 `R.data.attachmentId`，正式上报使用该 ID，不使用文件名或对象存储 URL。

当前异常证据每次上报最多 20 张、单张不超过 10MB，仅 JPG/JPEG/PNG。后端校验扩展名和真实可解码图像，图片边长不超过 12000、总像素不超过 2500 万。不可用 PDF 作为异常照片。上传成功仍为草稿；正式上报成功才消费为异常证据。

| 操作 | 接口 |
| --- | --- |
| 回显当前任务本人异常草稿 | `POST /tms/driverExecution/files/query`，请求 `entrustId,taskId,purpose=EXCEPTION` |
| 预览 | `GET /tms/driverExecution/files/{attachmentId}/preview`，返回文件流 |
| 下载 | `GET /tms/driverExecution/files/{attachmentId}/download`，返回文件流 |
| 删除未消费草稿 | `DELETE /tms/driverExecution/files/{attachmentId}` |

预览/下载携带 Bearer 令牌及租户头，小程序通过鉴权下载接口获取临时本地文件用于图片预览，不直接公开存储 URL。已被正式异常消费的证据不能再从司机入口删除。上传草稿的存在不代表异常单已生成。

### 7.4 正式提交异常

`POST /tms/driverExecution/exceptions/report`

对应页面：异常弹窗最终点击“提交上报”。

```json
  "attachmentIds": ["401", "402"],
  "materialCodesByOrder": {
    "301": ["<REAL_MATERIAL_CODE_FROM_ORDER_301>"]
  }
}
```

| 请求字段 | 必填 | 说明 |
| --- | --- | --- |
| 准备请求的 `entrustId,taskId,orderIds,stage` | 同准备接口 | 正式提交时重新授权并核对范围；相同任务上下文 |
| `requestId` | 是 | 8～64 位字母、数字、下划线或连字符；一个真实事件使用一个请求号 |
| `expectedVersion` | 是 | 最近一次 prepare 返回的版本，不可空白 |
| `categoryCode` | 是 | 七类之一；必须为当前 enabled 类别 |
| `level` | 是 | 当前类别 `levels[].code` 中的整数值；不是级别名称 |
| `description` | 是 | 非空白，最多 2000 字符；后端去除两端空白 |
| `attachmentIds` | 否 | 本人、当前任务、EXCEPTION 用途的有效草稿，最多 20 个；服务端核验真实归属 |
| `materialCodesByOrder` | 否 | JSON 对象键为本次 TO ID，值为此 TO 实际物料编码列表；不能带本次范围外订单或不真实的编码 |

未指定物料或某 TO 的物料列表为空时，表示关联该订单而不选择具体货物快照，不能理解为自动选中全部 SKU。任务级事件不传 `orderIds` 时仍会关联当前 TT 全部有效 TO，不会抓取整个 LD 下其他司机的任务订单。

成功 `R.data` 示例：

```json
{
  "exceptionId": "501",
  "exceptionNumber": "<GENERATED_EXCEPTION_NUMBER>",
  "status": 20,
  "statusName": "待受理",
  "reportTime": "<SERVER_REPORT_TIME>",
  "taskId": "201",
  "orderIds": ["301", "302"],
  "categoryCode": "DAMAGE",
  "level": 3,
  "attachmentCount": 2,
  "expectedVersion": "<RETURNED_VERSION>"
}
```

`exceptionId/exceptionNumber` 为正式后台异常单标识；`status/statusName` 来自原有异常提交链，成功进入待受理；`reportTime` 为服务端上报时间；`taskId/orderIds` 为本次实际关联范围；`attachmentCount` 为正式证据张数。返回版本不能替代下一次新事件前重新 prepare。

正式保存的来源为“物流商反馈”（40）；类型/名称/级别由真实后台规则决定。上报人、上报时间、异常时间、后台受理状态由后端生成，客户端不得提交责任人、处理结果或自行设置状态。原有异常单号、订单/物料快照、提交校验及异常日志链继续生效；PC 异常模块后续负责受理、定责与处理。

#### 7.4.1 重试与错误处理

- 网络超时且不确定结果时，用相同 `requestId` 和完全相同请求内容重试；已成功结果会重放，不重复创建异常。
- 同一 `requestId` 改变描述、附件、范围或版本会产生幂等内容冲突；不应靠反复换请求号重复创建同一事件。
- 后端明确返回版本过期时，重新 prepare，展示最新任务后由用户确认新的提交；新事件/重新确认采用新的请求号。
- 即使是成功请求的重试，也会重新检查当前任务归属；改派后不能靠旧请求号绕过授权。
- 描述空白、类别无规则、级别不可用、后台编码歧义、任务取消/挂起、无权订单、伪物料、过期/越权/用途不符证据均会失败；向用户展示后端原因，不伪造成功。

“异常签收”与“异常上报”是不同操作：签收接口保存当批 TO 处理结果和异常原因；只有此 `/exceptions/report` 创建正式运输异常单。本次上报不直接把整个 LD 状态改为派送异常。

## 8. 小程序必须补齐的交互与联调顺序

1. 复用项目当前账号密码登录并取得真实司机类型、租户司机映射的令牌，先调用 Q09/Q01 验证身份和任务范围。不要将普通平台账号仅凭手机号当司机。
2. Q01→Q02→W01→刷新版本→首点资料→W02；后续点按 nextPickupPointId 逐点确认，单点同时校验首点资料/末点凭证。
3. Q04→Q05 选真实包装→按 TO 上传 RECEIPT→W05 显示本次数量→W06 正式确认→Q06/Q07 核对每批 POD。
4. Q08 获取启用的类别和实际级别→照片草稿→W04 上报→核对 PC 异常待受理。取消时不调用上报。
5. 文件列表/预览/下载/合法删除、PC 撤回/改派/改量后刷新、同请求号重试、旧版本冲突分别联调。

原型缺少或未实际挂载完整控件，但 PRD 明确要求，小程序须接入：异常级别选择、异常签收原因、逐 TO 签收凭证上传与多份展示、历史附件查看/下载、符合状态的补传回单、独立补料入口（若列入页面）、运输记录和空轨迹提示。

“设置”、扫码、电子签名采集、独立发车/到达等缺少本期详细操作定义，本轮未凭概述添加新的写命令。原型已存在但未挂按钮的旧单 TO 签收、旧通用上传函数不再各造一套接口。
